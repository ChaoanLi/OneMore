# OneMore：一个账号、多个独立空间

日期：2026-10-23。状态：已完成独立设计审阅，待用户确认；尚未实施。

## 目的与已确认的选择

先实现两拨朋友互不混淆，再把项目上传到 GitHub。一个人可以同时属于两拨朋友。
用户已选择：一个网站、一个账号，可以切换多个独立空间。
空间不按国家、时区或服务器地区划分，由用户明确创建、加入和选择。

考虑过的方案：

1. **一个账号、多个空间（已选）**：统一登录，服务端按空间检查权限。需要同时改数据库、API、页面、分享链接及后台任务。
2. 两套独立站点和数据库：物理隔离直观，但账号、部署、维护重复，同一个人两边使用不便。
3. 仅使用现有“圈子”：不采用。圈子是个人好友分组，无法隔离成员目录、链接活动、通知和日历。

## 产品规则

- 账号身份共享：登录凭证、恢复码、昵称、头像、自定义 ID、时区、个人游戏偏好及已验证邮箱跟随账号。改昵称会影响该账号加入的所有空间，界面需说明。其他人不能查询某人加入了哪些空间。
- 空间之间独立：成员、好友关系、常玩好友、个人圈子、“我想玩”、活动、报名、邀请、站内通知、未读数、应用内日历、日历订阅、空间邮件开关。
- 只有当前空间的成员能查询本空间用户资料、添加好友或选择邀请对象。同一对人在 A 空间是好友，不代表在 B 空间也是好友。
- 活动的“持链接可报名”仅指**已加入该空间的成员**。空间外的人不能预览活动标题、地点、参与者或其他元信息。知道活动短码也不能绕过权限。
- 两边成员相互不可见；共同成员自己能切换空间，但任何一个空间不提供其他空间的成员、活动或统计信息。

以下是实现者建议的默认规则，随本设计一起交用户确认：

1. 创建空间的人是唯一管理员；其他人为成员。首版不做管理员转让、多管理员或删除整个空间。
2. 加入空间使用可撤销、可更换的随机邀请链接。管理员可以分享该链接；普通成员没有获取或更换链接的管理入口。
3. 邀请链接仅允许登录用户提交加入申请，**管理员批准后才成为成员**。不提供公开空间搜索，也不允许凭空间 ID 自助加入。
4. 邀请链接有效时只显示空间名称和申请状态；不显示成员、管理员资料或活动。换链接后旧链接不能提交新申请；已提交申请仍由管理员批准或拒绝。
5. 管理员可查看成员和加入申请、批准、拒绝和移除成员；普通成员可退出。管理员不能移除自己或退出自己拥有的空间。
6. 退出或被移除后，权限及该成员的空间日历订阅立即失效，并取消尚未发送的空间活动邮件。历史报名和已发内容留在原空间，供原有成员理解活动记录；不做删除历史身份的功能。
7. 不自动把任何现有账号加入公共默认空间；新账号先创建空间或使用邀请链接申请加入。

独立审阅指出退出及重新加入时需要明确以下规则。实现者提出这些默认选择，一并交用户确认：

- 退出或被移除的人，其未结束的主办活动取消，仍有效的想玩撤回，相关成员收到该空间内的状态通知。不自动把主办权交给管理员。
- 此人在其他人的未来活动中的邀请、回应、正式/候补席位及有效想玩中的参与撤回，按原有规则重新计算人数和状态并通知主办人；不自动把候补变成正式成员。已结束或已取消活动的记录保持历史状态。
- 本空间内与此人的好友关系、偏好、个人圈子以及其他圈子中的该成员引用清理。旧通知不带入下一次成员资格；旧空间邮件设置和日历订阅作废。其他空间中的任何关系不变。
- 重新获批加入时视为新的成员资格：没有自动恢复的好友、邀请、报名、通知或订阅，空间邮件开关重新使用新成员默认值。本人有权查看的本空间历史活动仍按普通成员的活动可见规则访问。
- 权限撤销、活动/参与状态调整、关系清理及待发邮件取消以事务保证一致性。通知面向仍有资格的成员，不能把其他空间或被移除成员重新引入收件名单。

## 页面与使用流程

- 登录后无空间：显示“创建空间 / 通过邀请加入”，不显示旧的全局活动或好友页面内容。
- 页面顶部始终显示当前空间名称和切换入口。空间选择页只列出本人已加入的空间；管理入口只对管理员显示。
- 分享邀请进入申请页；批准前只能看到申请状态。成员管理和申请处理在空间管理页完成，不额外发送邮件或外部消息。
- 同时属于 A/B 的人从 A 切到 B：清空页面内容、活动草稿、好友预选、通知未读数和日历结果，再加载 B。A 未完成的网络请求不能覆盖 B。
- 分享、邮件及日历的活动链接携带空间标识；打开时验证本人有该空间成员资格，成功后明确切换到该空间再取数据。无资格时显示统一的无权访问提示，不自动申请或自动加入。
- 直接访问旧的纯活动短码链接必须先选择空间并通过授权；不通过跨空间搜索来猜测活动所属空间。
- 邀请加入空间与邀请参加活动是两个独立动作，活动链接不能成为加入空间的后门。

## 存储与服务端边界

保留当前 Node/Hono/SQLite 单站部署，使用一个数据库实现逻辑空间隔离，不引入额外云服务。

- 全局保存账号、登录会话、恢复凭证、邮箱验证状态，以及空间和成员关系。
- 新增空间、成员关系、邀请令牌哈希、加入申请和成员空间设置。管理员也是成员；申请批准操作在事务中检查角色和状态，重复申请/批准不会产生重复成员。
- 所有空间业务表都有不可为空的空间标识：好友、好友偏好、圈子、活动、活动邀请、回应、想玩、通知、日历订阅、空间邮件记录。需要唯一性的键包含空间标识（例如同一对人可在两个空间分别建立好友关系）。
- API 从已验证的 Bearer 会话取用户，再从请求的明确空间标识检查成员关系。缺少空间不默认读取全局数据。空间 ID 是定位信息，不是授权凭证。
- 为每个请求创建不可变的空间上下文/存储视图，禁止修改全局 Store 的“当前空间”。所有业务读写都通过该上下文；请求体中的空间字段不能覆盖已授权上下文。
- 数据读取、更新、删除都同时约束对象 ID 和当前空间。外空间 ID/短码得到统一的不存在或无权结果，不返回该对象是否存在、归属哪个空间或对象摘要。
- 批量邀请、圈子成员、报名参与者、成团名单、候补、从想玩转活动及 AI 草稿中的好友预选都验证当前空间成员和现有业务权限。外空间引用返回输入错误，不能静默跨空间导入。
- 账号资料接口只允许读取自己，或在授权空间内查询该空间成员的最少公开资料；其他空间的成员列表不参与查询。
- 历史活动中已退出成员的最少公开资料可在该活动内展示；这不授予全局账号搜索权限。退出成员不再出现在新增邀请、好友发现或成员候选中。
- 管理权限每次请求重新检查；移除成员后已有登录令牌不再能访问该空间。应用内通知标记已读只影响当前空间。

## 邮件、日历与后台任务

- 邮箱验证属于账号层，只需验证一次；空间邮件开关独立。保留现有全邮箱退订作为总开关，界面明确其影响所有空间。
- 原来的“邮件邀请活动”只能发给当前空间中已验证邮箱的成员；给陌生邮箱发送活动信息不在首版支持。管理员通过空间加入链接邀请新人。
- 活动邮件正文及主题包含所属空间名称，链接绑定该空间。空间业务发件项保存空间、接收成员及对象引用；实际发送前重新检查成员资格、邮件开关和对象可见权限，避免排队后权限撤销仍发送详情。
- 未知邮箱、未批准申请人和已退出成员不能收到空间活动内容。全局邮箱验证码不携带空间活动信息。
- 每人每空间独立的 ICS 订阅令牌（数据库只存哈希），令牌定位唯一的用户+空间。每次订阅请求检查成员资格，仅输出该空间内本人有权订阅的活动；单空间重置/关闭不影响另一空间。
- 旧的无空间日历令牌失效，需要在空间内重新生成。客户端已经下载的邮件或第三方日历缓存无法撤回，界面说明订阅是私密链接。
- 定时清理想玩、刷新活动和发件队列显式遍历空间并建立各自上下文；不能借后台全局入口重新扩大可见范围。无空间的旧发件项不得自动发送。

## 现有本地数据的处理

当前本地已有 SQLite 文件，原模型没有空间归属，不能可靠推断这些数据应该属于哪拨人。

默认采取保留、隔离、不自动合并：

- 升级前进行一致性数据库备份；不删除现有账号和业务数据，也不上传数据库到 GitHub。
- 全局账号和登录凭证继续有效。没有空间字段的旧业务数据进入不可被普通 API 访问的历史隔离区；旧日历令牌及旧活动发件队列停止服务/发送。
- 新空间从空白开始。提供仅在服务器本地运行的显式迁移命令及说明：操作者指定目标空间和确切旧成员清单，预览后才导入符合清单的关联数据。不得自动把所有旧用户加入同一个空间。
- 旧活动及其所有参与者、邀请者、报名者、圈子成员、想玩参与者必须完整属于指定清单才可迁移；存在跨清单引用时跳过整个相关对象并报告数量及原因，不悄悄扩大成员或截断参与关系。历史通知、旧发件任务、旧订阅令牌不恢复。
- 迁移使用事务、显式归属和版本记录；重复启动不重复修改数据。演示 seed 改为明确的演示空间，仅在显式运行 seed 时创建，不在生产启动自动执行。

## 验收证据

以 A 空间、B 空间、同时属于 A/B 的用户和完全不属于任何空间的用户构建测试：

1. 同一个账号切换后，好友、圈子、想玩、活动、通知、未读、日历互不串组；相同好友对可在两空间独立操作。
2. 伪造空间 ID、活动短码、圈子 ID、想玩 ID、接收成员及成团名单，不能跨空间读写。匿名访问或转发“持链接”活动不会泄露活动详情。
3. 并发 A/B 请求的上下文不能串用；A 的慢响应和未提交草稿不能出现在 B，退出/切换账号会清空空间状态。
4. 邀请链接更换、申请批准/拒绝、非管理员管理操作、移除成员、退出与重新加入的权限都符合规则。退出后未结束的主办活动取消、未来活动参与撤回、人数重新计算；重新加入不恢复旧好友、邀请、参与、通知、订阅和待发邮件。另一空间中的关系及活动不受影响。
5. 成员被移除后，站内 API、ICS 和延迟发件均失效；A 的通知已读或订阅重置不影响 B。
6. 旧数据库升级、备份与迁移可验证；没有归属的数据不会因兼容分支重新被访问。原有业务测试更新到明确空间后仍通过。
7. 运行测试、各 workspace 的类型检查与 H5 生产构建；浏览器检查创建、申请/批准、切换、活动分享、无权限页面及小屏布局。记录未能验证的外部服务。
8. GitHub 仓库中只有预期源码文件，没有实际凭证、用户数据或本机云资源记录。

## 范围与留给实现者的决定

此轮完成空间隔离及 GitHub 上传；Oracle 容量、真实部署、域名 DNS、SMTP 服务商与 DeepSeek 凭证接入继续保留为后续工作，不因上传仓库宣称上线。

不增加组织计费、跨空间搜索、跨空间邀请、空间合并、多个管理员或自动判断用户属于哪拨人。空间成员可以看到同空间历史活动中的原参与者，这是成员移除后的保留规则。

具体表命名、请求头或 URL 结构、组件拆分、迁移实现和测试组织由实现者选择，只要统一实现上述授权及数据边界；优先复用现有代码和样式，不引入无必要的依赖。
